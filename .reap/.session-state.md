## v0.17.1

# v0.17.1 — Vision Memory Content-Type Reorganization

## What changed

Up through v0.17.0, REAP's vision memory tiers (`.reap/vision/memory/{shortterm,midterm,longterm}.md`) were classified by **lifespan** — "how long will this live?" That heuristic forced the AI to predict the future and led to repeated misclassification + bloat.

Starting with v0.17.1, tiers are classified by **content-type** — "what is this content for?" The decision is now mechanical and bloat-resistant.

| File | Role (new) | 1-line decision rule |
|------|------------|----------------------|
| `shortterm.md` | **Session handoff** — immediate context for the next session | "Is this needed right now?" |
| `midterm.md`   | **Ongoing tracks** — multi-generation work in progress | "Is this an incomplete large track?" |
| `longterm.md`  | **Design lessons** — recurring lessons worth re-reading | "Does this lesson prevent the next generation from making the same mistake?" |

A mandatory **reflect-phase pruning policy** was also added: shortterm is replaced (not appended) every generation, midterm sections get deleted on track completion (key decisions promoted to longterm), and longterm gets periodic dedup vs genome.

See `~/.reap/reap-guide.md` § Memory and `.reap/genome/evolution.md` § Vision 활용 원칙 for the full rules.

## Required actions for the AI agent

Apply these in order. Do **not** treat this as a code change — it is an artifact reorganization. No source code is touched.

1. **Read** the current state of all three memory files:
   - `.reap/vision/memory/shortterm.md`
   - `.reap/vision/memory/midterm.md`
   - `.reap/vision/memory/longterm.md`

2. **Reclassify each entry** using the new decision tree (apply top-to-bottom):
   ```
   1. Is this needed in the next session immediately?     → shortterm.md
   2. Is this an ongoing, incomplete track or plan?       → midterm.md
   3. Is this a finished design lesson worth preserving?  → longterm.md
   4. Finished, no special lesson?                        → DELETE (lineage + git history preserve it)
   ```

3. **Move misclassified entries** to the correct tier. Typical patterns to fix:
   - "Will be useful eventually" / "background context" sitting in `longterm.md` but not driving any current behavior → delete
   - Completed track summaries in `midterm.md` without a next step → delete (promote one-line lessons to `longterm.md` only if they prevent future mistakes)
   - Stale session handoffs from earlier generations in `shortterm.md` → delete (shortterm is **replaced** every generation, not appended)

4. **Apply the size-bloat heuristics**:
   - `longterm.md` should stay under ~30–50 lines. Over that = pruning was skipped.
   - `midterm.md` should stay under ~50–70 lines. Over that = completed tracks weren't removed.
   - `shortterm.md` should contain only the most recent 1–2 generations' handoff.

5. **Do NOT add new entries** during this migration. Goal is reorganization of what already exists. New lessons land in the next generation's normal reflect.

6. **Verify** the new classification by re-applying the decision tree to each entry one more time. If you can't justify keeping an entry under any of branches 1–3, delete it.

7. **Run** `reap update --mark-migrated` to record completion. This sets `lastMigratedVersion: 0.17.1` in `.reap/config.yml` so this instruction stops surfacing in subsequent SessionStart loads and `reap update` runs.

# v0.17.5 — Add the evidence-kind rule to genome/evolution.md

## What changed in REAP

REAP now asks agents to record **what kind of evidence** stands behind each verification claim, instead of writing "verified" for everything. The rule ships in `src/templates/evolution.md`, so new projects get it from `reap init` — but **REAP never overwrites an existing project's genome**, which is why this note exists.

The rule came out of two consecutive REAP generations in which the same failure appeared:

- gen-083 recorded an item as satisfied that nothing had actually executed. An independent evaluator caught it while every test was green.
- gen-084 adopted a tagging convention to prevent exactly that, and then failed **one row over** — the behaviour under test was correct, but no command in the gate or the suite exercised it.

"It was correct" is not an answer to this problem. A claim nobody ran is unverified whether or not it happens to be true.

Normally the genome changes only during `completion --phase adapt`. **This note is an explicit exception, limited to v0.17.5**, because the rule concerns how agents write artifacts in every generation and cannot wait for one. Do not treat it as a precedent.

```markdown
### Record what kind of evidence you have — and "ran it" must name the command

Writing only "verified" in an artifact makes **running the command and reading the code look the same.** That distinction collapsed in two consecutive generations, and a blocking defect came through each time.
```

## v0.17.6

# v0.17.6 — the daemon is gone; the indexer is built in

REAP no longer ships a resident process. `@c-d-cc/reap-daemon` is retired
(deprecated on npm), and the code index now lives inside `reap` itself.

Nothing here is urgent. `reap` works unchanged if you do nothing; these steps
remove settings that stopped meaning anything and data nothing reads.

## 1. `config.yml` — `daemon` and `daemonBin` are no longer valid

If your `.reap/config.yml` contains either field, **`reap update` has already
removed it** by the time you read this — it prunes fields that are no longer
valid and reports the removal in its output.

That is the intended outcome, not a loss. There is no resident process to enable
and no binary to point at. The index is built by `reap index` and refreshed by
the commit at the end of each generation.

**No action needed.** If you kept a copy of your config, do not restore either
field: `reap update` will remove it again.

## 2. `~/.reap/daemon/` — removed for you

The daemon kept a registry of indexed project paths and one SQLite symbol graph
per project under `~/.reap/daemon/`. Nothing writes or reads it now, and
`reap update` deletes the directory.

**No action needed.** Only that one entry is touched — anything else you keep in
`~/.reap/` is left alone.

## 3. If you installed the daemon package globally

Check and remove it:

```bash
npm ls -g --depth=0 @c-d-cc/reap-daemon   # is it there?
npm uninstall -g @c-d-cc/reap-daemon      # if so
```

`reap uninstall` also names it, so you do not need to do this by hand unless you
are staying and simply want the disk back.

**Kill a stray process if you have one.** The daemon stayed resident for thirty
idle minutes and, in at least one observed case, survived as an orphan its own
`reap daemon stop` could not find:

```bash
lsof -iTCP:17224 -sTCP:LISTEN    # nothing should answer
```

## 4. What replaces it

```bash
reap index status               # counts, import resolution rate, indexed commit
reap index search <query>       # find a definition
reap index impact <file>        # what breaks if you change this file
reap index callers <symbolId>   # symbolId looks like src/core/lifecycle.ts::fn
```

There is nothing to start. Queries refresh the index themselves when `HEAD` has
moved, and the generation's commit refreshes it eagerly.

The index is written to `.reap/.index/` in each project — **not** to your home
directory. **`reap update` adds it to `.gitignore` for you**, which is why this
step needs nothing from you beyond having run `reap update` once.

It appends only when no line already names that directory, so if you had
already ignored it yourself nothing changes. A *broader* rule you may have —
`.reap/` on its own — is not recognised, and you will get a redundant entry.
Harmless, and you can delete it.

Committing the index would mean the commit containing it has to be indexed,
which is a loop — and `reap run completion --phase commit` runs `git add -A`,
so an unignored index would be committed on every generation.

## 5. One behaviour worth knowing

**The index is keyed by commit.** Symbols you have written but not committed are
not in it. `reap index status` always shows which commit the index describes, so
you can see when that matters. Use ordinary search for uncommitted work.

If you use `daemon: true` in a project that also pinned a REAP version below
0.17.6, nothing breaks — the old code simply finds no daemon, which is what it
already did.
